\section{Purpose and Scope}

This document is an architectural description of the CommandIA repository and
of its branches. It was produced by inspecting the Git history, the file trees
of all local and remote branches, and the source files themselves.

The document covers:

\begin{itemize}[leftmargin=1.2em]
  \item the branch topology and how the branches relate to each other;
  \item the logical and physical architecture of the \code{main} branch;
  \item each runtime component, its responsibilities and its interfaces;
  \item the conversation state machine, the data contracts and the database
        schema;
  \item the test architecture and the deployment architecture;
  \item the architecture of each feature, initial and AI branch;
  \item the observed architectural risks and the remaining technical debt.
\end{itemize}

It is not an installation manual. The operational commands are grouped in
Appendix B for convenience.

\section{Executive Summary}

CommandIA is a conversational engine for Algerian e-commerce. It receives
customer messages from Instagram or Facebook direct messages, answers product
questions in Algerian Darija, Franco-Arabic, French or English, guides the
customer through an order, extracts the five required delivery fields, and
writes a structured order to Supabase.

The repository has evolved through two largely independent work streams:

\begin{enumerate}[leftmargin=1.2em]
  \item an \textbf{AI stream}, carried by \code{ai\_model\_part} and then by
        the local \code{main} branch, which contains the Gemini-based AI Brain,
        the Pydantic contracts, the state machine, the FastAPI service, the
        Supabase writer, the offline test suite and the Docker image;
  \item a \textbf{backend and webhook stream}, carried by
        \code{initial-backend}, \code{feat/meta-webhook} and
        \code{origin/feat/metaWebhook}, which contains the first FastAPI
        application, the PostgreSQL schema, the local Meta webhook emulator and
        a direct Supabase insertion pipeline.
\end{enumerate}

The local \code{main} branch is the current integration branch. It contains
both the AI module and the legacy backend application, plus the Docker and
Compose configuration. The remote \code{origin/main} branch does not yet
contain the AI module. The \code{ai\_model\_part} branch is an AI-only line
based on the AI tip; it adds a database-contract test and a schema aligned with
the canonical order contract.

The most important architectural divergence is the database contract:
\code{order\_store.py} writes the canonical columns
(\code{order\_id}, \code{wilaya}, \code{product\_details},
\code{order\_status}), while the SQL schema on \code{main} still uses
\code{id}, \code{wilaya\_code}, \code{wilaya\_name} and \code{status}. The
\code{ai\_model\_part} branch corrects the schema, but its contract test
references a symbol that is not yet defined on that branch.

\section{Main Branch: Logical Architecture}

\subsection{Architectural Style}

The \code{main} branch is a \textbf{modular layered monolith}:

\begin{itemize}[leftmargin=1.2em]
  \item a presentation and integration layer implemented by FastAPI
        (\code{app.py}) and by the command-line tools;
  \item a service layer implemented by \code{ai\_service.py}, which owns the
        in-memory conversation registry;
  \item a domain and AI layer implemented by \code{ai\_brain.py}, the system
        prompt, the Pydantic schemas and the wilaya registry;
  \item an integration layer for external services: the Gemini API and the
        Supabase REST API;
  \item a deployment layer implemented by the Dockerfile and Compose file.
\end{itemize}

Conversations are held in a Python dictionary inside the process. The HTTP
service is therefore stateless with respect to persistence, but conversation
state is process-local and is lost when the container restarts.

\subsection{Webhook Processing}

The Meta webhook is designed around the twenty-second Meta timeout:

\begin{enumerate}[leftmargin=1.2em]
  \item The raw request body is read and the \code{X-Hub-Signature-256}
        header is checked with HMAC-SHA-256 against \code{META\_APP\_SECRET}.
        A missing secret causes a 503, an invalid signature a 403.
  \item The JSON body is parsed and flattened with \code{\_extract\_messages}.
        Entries without text and echo messages are ignored.
  \item Every message identifier is registered with \code{\_remember\_message}.
        The registry is a set plus an ordered list capped at 2000 identifiers,
        so a Meta retry does not answer twice while memory stays bounded.
  \item Each fresh message is scheduled as a FastAPI background task and the
        endpoint immediately returns \code{\{"status": "ok", "received": n\}}.
  \item \code{\_handle\_incoming\_message} calls the AI service, optionally
        saves an order with \code{OrderStore}, and sends the reply through the
        Graph API.
\end{enumerate}

\subsection{AI Service}

\code{AIService} is a thin orchestration layer around \code{AIBrain}. Its
state is a dictionary \code{\_conversations} mapping a conversation identifier
to a \code{ConversationState}. The main methods are:

\begin{itemize}[leftmargin=1.2em]
  \item \code{process\_message(user\_message, conversation\_id, product\_context)}:
        retrieves or creates the state, delegates to the brain, stores the
        updated state and returns the result;
  \item \code{get\_conversation\_state(conversation\_id)}: returns the current
        state, collected fields, missing fields, escalation flag, attempts and
        language;
  \item \code{reset\_conversation(conversation\_id)}: replaces the state with a
        fresh one;
  \item \code{delete\_conversation(conversation\_id)}: removes the state.
\end{itemize}

Because the registry is a plain dictionary, the service is not safe for
multi-process horizontal scaling without an external store.

\subsection{AI Brain Pipeline}

For every user message, \code{AIBrain.process\_message} executes the following
pipeline:

\begin{enumerate}[leftmargin=1.2em]
  \item create or reuse a \code{ConversationState};
  \item merge the optional product context into the state;
  \item detect the language and lock it on the first turn;
  \item increment the attempt counter and build the history of the last five
        exchanges;
  \item assemble the full prompt from the system prompt, the current state,
        the collected and missing fields, the product context, the history and
        the latest message;
  \item call Gemini through \code{\_generate\_content};
  \item parse the JSON response, accepting an optional Markdown code fence;
  \item sanitize the extraction so one malformed field does not discard the
        whole order;
  \item validate the result with the Pydantic \code{OrderExtractionResponse};
  \item update the conversation state, the missing fields, the escalation
        status and the order status;
  \item build and return the canonical extraction plus the legacy
        compatibility keys.
\end{enumerate}

On a provider or validation error, the pipeline does not raise into the
webhook. It builds a degraded result with a localized fallback reply and an
\code{error} field.

\subsection{Gemini Client, Retries and Model Fallback}

The Gemini call is configured with:

\begin{itemize}[leftmargin=1.2em]
  \item \code{temperature = 0.3}, \code{top\_p = 0.95},
        \code{top\_k = 40} and \code{max\_output\_tokens = 2048};
  \item \code{response\_mime\_type = application/json} and the
        \code{OrderExtractionResponse} response schema, so the provider is
        asked for structured output.
\end{itemize}

The model chain is the primary model followed by
\code{GEMINI\_MODEL\_FALLBACKS}, deduplicated while preserving order.
Transient errors are retried; configuration and authentication errors are not.

\begin{table}[H]
\centering
\small
\begin{tabularx}{\linewidth}{@{}l X@{}}
\toprule
Rule & Behaviour \\
\midrule
Transient status codes & 408, 409, 429 and all 5xx responses are retried. \\
Permanent errors & 400, 401, 403 and 404 are not retried; the next model in
  the chain is tried instead. \\
Backoff & Exponential: \code{RETRY\_BASE\_DELAY} multiplied by
  \(2^{attempt-1}\). \\
Provider hint & If the provider message contains ``retry in N s'', the wait is
  the larger of the exponential delay and the provider delay. \\
Cap & Every wait is capped at \code{RETRY\_MAX\_DELAY}. \\
Exhaustion & When all models and attempts fail, the last error is raised to
  the brain, which returns a fallback result. \\
\bottomrule
\end{tabularx}
\caption{Retry and model-fallback policy.}
\end{table}

\subsection{Language Detection and Mirror Rule}

\code{\_detect\_language} uses deterministic heuristics, not an API call:

\begin{enumerate}[leftmargin=1.2em]
  \item if more than thirty percent of the characters are in the Arabic
        Unicode ranges, the message is \code{darija};
  \item Franco-Arabic phrases, digit-letter markers such as
        \code{3andkom} or \code{9ndek}, and a marker lexicon identify
        \code{franco\_arabic};
  \item French marker words identify \code{french};
  \item English marker words and phrases identify \code{english};
  \item the default is \code{french}, except for an empty message, which
        defaults to \code{franco\_arabic}.
\end{enumerate}

The PRD mirror rule is implemented by storing \code{initial\_language} on the
first turn and reusing it for every later turn. Digits alone are never a
language signal, so a French sentence containing a price remains French.

\subsection{Extraction Sanitization}

The model can return a slightly malformed field. \code{\_sanitize\_extraction}
normalizes before strict validation:

\begin{itemize}[leftmargin=1.2em]
  \item phone numbers are normalized; invalid numbers become \code{None};
  \item wilaya codes are converted to integers and kept only when they map to
        a known wilaya;
  \item delivery types are uppercased and kept only when they are
        \code{HOME} or \code{DESK};
  \item unknown order statuses fall back to \code{PENDING\_CONFIRMATION};
  \item malformed order items are dropped; quantities are coerced to at least
        one; negative prices become \code{None};
  \item negative totals become \code{None}; a non-string reply is coerced.
\end{itemize}

This design prevents the most damaging failure mode: losing a complete order
because a single field was malformed.

The phone normalizer accepts the formats customers actually type:
\code{0550123456}, \code{0550 12 34 56}, \code{+213 550 12 34 56},
\code{00213 550 12 34 56} and dashed forms. It removes non-digits, strips the
international prefixes, adds a leading zero to a nine-digit mobile number, and
then requires a ten-digit number starting with 05, 06 or 07.

\subsection{Wilaya Registry}

\code{wilayas.py} defines \code{WILAYA\_CODE\_TO\_NAME} for codes 1 to 69 and
provides:

\begin{itemize}[leftmargin=1.2em]
  \item \code{get\_wilaya\_name(code)}: code to canonical name;
  \item \code{get\_wilaya\_code(name)}: name or alias to code;
  \item \code{is\_valid\_wilaya(value)}: name or code validation;
  \item \code{normalize\_wilaya(name)}: accent-insensitive canonicalization;
  \item alias handling for spellings such as \code{algiers}, \code{setif} and
        \code{msila}.
\end{itemize}

The PRD mentions 58 wilayas, while the implementation uses 69 codes. This is a
documentation and specification gap, not a code defect.

\subsection{System Prompt and Business Guardrails}

\code{system\_prompt.py} contains the V1 prompt. It defines:

\begin{itemize}[leftmargin=1.2em]
  \item the assistant identity and the commercial objective;
  \item the four supported languages and the mirror rule;
  \item the five sacred fields and their validation rules;
  \item the conversational state machine;
  \item the JSON output shape;
  \item the guardrails: no unauthorized discount, haggle defense, dynamic
        shipping, focus on the sale and human handoff.
\end{itemize}

The prompt is assembled at runtime with the current state, the collected and
missing fields, the product context, the history and the latest user message.

\subsection{Order Persistence}

\code{OrderStore} writes through the Supabase REST API, so the runtime has a
single HTTP dependency, \code{httpx}, and no database driver. The canonical
columns are:

\begin{lstlisting}[language=Python]
ORDER_COLUMNS = (
    "order_id",
    "customer_name",
    "phone_number",
    "wilaya",
    "delivery_type",
    "address",
    "product_details",
    "total_price_da",
    "order_status",
)
\end{lstlisting}

The writer posts to \code{<SUPABASE\_URL>/rest/v1/<table>} with the
\code{apikey} header, a bearer token, a JSON content type and
\code{Prefer: return=minimal}. It returns \code{False} on any HTTP or network
error and only logs the failure, so persistence never blocks the customer
reply. The feature is disabled when the URL or the key is empty or still a
placeholder.

\subsection{Command-Line and Manual Tools}

\section{End-to-End Flows}

\subsection{Instagram or Facebook DM Flow}

\begin{lstlisting}[caption={Main branch DM flow}]
Meta customer
  -> Instagram or Facebook DM
  -> Meta Graph API webhook POST /webhook
  -> app.py verifies X-Hub-Signature-256
  -> app.py deduplicates message.mid
  -> app.py returns 200 immediately
  -> background task _handle_incoming_message
  -> AIService.process_message
  -> AIBrain detects language and builds prompt
  -> Gemini returns structured JSON
  -> sanitize, Pydantic validation, state update
  -> optional OrderStore.save_order to Supabase
  -> Graph API POST /me/messages sends the reply
  -> Meta delivers the reply to the customer
\end{lstlisting}

\subsection{Development Chat Flow}

\begin{lstlisting}[caption={Main branch /chat flow}]
HTTP client
  -> POST /chat with X-API-Key
  -> app.py checks COMMANDIA_API_KEY
  -> AIService.process_message
  -> AIBrain and Gemini
  -> JSON response with reply, language, state,
     missing fields, collected fields, extracted data,
     order data and conversation id
\end{lstlisting}

\subsection{Legacy Backend Webhook Flow}

The legacy \code{backend/main.py} implements a simpler and less protected
path:

\begin{lstlisting}[caption={Legacy backend flow}]
Meta webhook POST /webhook
  -> parse payload object == "instagram"
  -> extract sender id and message text
  -> AIService.process_message
  -> optional OrderStore.save_order
  -> on AI error: create_mock_order in Supabase
  -> return {"status": "success"}
\end{lstlisting}

This path does not verify the Meta signature and does not deduplicate message
identifiers. It also falls back to inserting a mock order when the AI fails,
which is useful for a demo but dangerous in production.

\subsection{Error and Degraded Flow}

When Gemini fails permanently or the response cannot be validated,
\code{AIBrain} returns a degraded result instead of raising:

\begin{itemize}[leftmargin=1.2em]
  \item a localized fallback message in French, English, Darija or
        Franco-Arabic;
  \item an order extracted from the fields already collected;
  \item \code{REQUIRES\_HUMAN} when the conversation is escalated, otherwise
        \code{PENDING\_CONFIRMATION};
  \item an \code{error} field describing the provider or validation problem.
\end{itemize}

\section{Conversation State Machine and Business Rules}

\subsection{States}

\begin{table}[H]
\centering
\small
\begin{tabularx}{\linewidth}{@{}l l X@{}}
\toprule
State & Name & Behaviour \\
\midrule
0 & \code{INQUIRY} & The customer asks about price, size, colour or
  availability. The assistant answers and may offer to take an order. \\
1 & \code{ORDER\_INTENT} & The customer signals a purchase intention. Data
  collection starts. \\
2 & \code{DATA\_COLLECTION} & The assistant asks for the missing sacred fields,
  one at a time. \\
3 & \code{CONFIRMATION} & All five fields are valid. The assistant summarizes
  the order and asks for explicit confirmation. \\
-- & \code{ESCALATION} & Human handoff because of frustration, a bulk-pricing
  request or three failed data-collection attempts. \\
\bottomrule
\end{tabularx}
\caption{Conversation states.}
\end{table}

\subsection{Transition Logic}

The transition is deliberately conservative. The resolution order in
\code{\_update\_conversation\_state} is:

\begin{enumerate}[leftmargin=1.2em]
  \item if the state is escalated, move to \code{ESCALATION};
  \item if there are no missing fields, move to \code{CONFIRMATION};
  \item if at least one field has been collected, move to
        \code{DATA\_COLLECTION};
  \item if the previous state was \code{ORDER\_INTENT} or
        \code{DATA\_COLLECTION}, stay in that state; a garbled turn must not
        send an open order back to inquiry;
  \item if the previous state was \code{CONFIRMATION}, move to
        \code{DATA\_COLLECTION} so a correction can be collected;
  \item if a purchase-intent marker is present, move to
        \code{ORDER\_INTENT};
  \item if the model reports \code{ORDER\_INTENT}, move to
        \code{ORDER\_INTENT};
  \item if the model reports \code{DATA\_COLLECTION} and items exist, move to
        \code{DATA\_COLLECTION};
  \item otherwise, move to \code{INQUIRY}.
\end{enumerate}

\subsection{The Five Sacred Fields}

\begin{table}[H]
\centering
\small
\begin{tabularx}{\linewidth}{@{}c l X@{}}
\toprule
Number & Field & Validation rule \\
\midrule
1 & \code{customer\_name} & Contains at least a first name. \\
2 & \code{phone\_number} & Algerian mobile: ten digits starting with 05, 06 or
  07. International and spaced forms are normalized first. \\
3 & \code{wilaya\_code} & Identifies one of the 69 supported wilayas. \\
4 & \code{delivery\_type} & \code{HOME} for home delivery or \code{DESK} for
  stop-desk, relay point or office delivery. \\
5 & \code{address} & Commune, street or clear location for home delivery; the
  commune or agency for desk delivery. \\
\bottomrule
\end{tabularx}
\caption{The five sacred fields.}
\end{table}

\subsection{Pricing Rule}

The prompt and the state machine use the following rule:

\[
  \text{subtotal} = \sum_{i} \left(\text{unit price}_{i} \times
  \text{quantity}_{i}\right)
\]
\[
  \text{total} = \text{subtotal} + \text{shipping fee}
\]

The shipping fee is applied once per order, based on the wilaya and the
delivery type; it is never multiplied by the number of items.

\subsection{Confirmation and Escalation Guardrails}

\begin{itemize}[leftmargin=1.2em]
  \item The model may claim \code{CONFIRMED}, but the service only accepts it
        when all five fields are valid and the user message contains an
        explicit confirmation marker such as \code{yes}, \code{confirm},
        \code{oui}, \code{d'accord} or \code{n3am}.
  \item A model-provided \code{REQUIRES\_HUMAN} sets the escalation flag.
  \item Three failed data-collection attempts without a new valid field also
        escalate.
  \item Once escalated, the state remains \code{ESCALATION} and the order
        status remains \code{REQUIRES\_HUMAN}.
  \item The price guardrails forbid unauthorized discounts and require a
        polite refusal of haggling.
\end{itemize}

\subsection{Database Schema on the Main Branch}

The legacy \code{backend/schema.sql} defines three enum types and seven
tables:

\begin{itemize}[leftmargin=1.2em]
  \item \code{delivery\_option}: \code{HOME}, \code{DESK};
  \item \code{order\_status}: \code{PENDING\_CONFIRMATION}, \code{CONFIRMED},
        \code{REQUIRES\_HUMAN}, \code{CANCELLED};
  \item \code{conversation\_state}: \code{INQUIRY}, \code{ORDER\_INTENT},
        \code{DATA\_COLLECTION}, \code{CONFIRMATION}, \code{COMPLETED},
        \code{ESCALATED};
  \item \code{merchants}: store name, Meta page id, access token and
        desk-delivery flag;
  \item \code{products}: merchant, name, price and stock quantity;
  \item \code{conversations}: merchant, customer Instagram id, current state,
        bot-active flag and last message time;
  \item \code{messages}: conversation, sender type, text and raw payload;
  \item \code{shipping\_rates}: merchant, wilaya code, home fee and desk fee;
  \item \code{orders}: the five fields, totals, status and timestamps;
  \item \code{order\_items}: order, product, extracted product name, quantity,
        unit price and JSON attributes;
  \item \code{update\_modified\_column()}: trigger function that updates the
        order timestamp.
\end{itemize}

The relationships are: a merchant owns products, conversations, shipping rates
and orders; a conversation owns messages and may own orders; an order owns
order items; an order item may reference a catalog product.

fails at import time until the writer is updated. This is the main incomplete
integration point of that branch.

delay, but running the golden dataset and the manual script back to back can
still exhaust the quota. They must be run separately.

  \item set \code{PYTHONDONTWRITEBYTECODE}, \code{PYTHONUNBUFFERED},
        \code{PIP\_NO\_CACHE\_DIR} and \code{PORT=8000};
  \item copy \code{requirements.txt} and install the dependencies;
  \item copy the application;
  \item conditionally change ownership to the \code{commandia} user;
  \item expose port 8000;
  \item add a healthcheck that calls \code{http://127.0.0.1:8000/healthz};
  \item run \code{uvicorn app:app --host 0.0.0.0 --port 8000}.
\end{itemize}

The documentation describes a \code{python:3.12-slim} base image, but the
current Dockerfile builds from \code{ai-base-env:latest}. The current file also
does not contain a \code{USER} directive; the ownership change alone does not
switch the runtime user.

\code{.dockerignore} excludes \code{.env} and \code{.env.*} except the template,

environments and egg metadata.

The legacy \code{backend/main.py} contains a hard-coded fallback verify token,
and \code{backend/force\_link.py} contains a hard-coded access token. These are
security risks: the tokens must be rotated, removed from the source and loaded
only from the environment.

\section{Architectural Decisions, Risks and Technical Debt}

\subsection{Decisions}

\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Prompt engineering rather than fine-tuning}: the PRD asks for
        prompt engineering; the AI Brain uses a versioned system prompt and
        structured output.
  \item \textbf{Gemini rather than OpenAI or Anthropic}: the implementation
        uses the \code{google-genai} SDK, while the PRD mentions OpenAI and
        Anthropic. The documentation is older than the code.
  \item \textbf{Supabase through REST rather than a database driver}: this
        keeps the runtime dependency surface small and works from a container.
  \item \textbf{In-memory conversation registry}: simple and sufficient for a
        demo, but not durable and not horizontally scalable.
  \item \textbf{Defensive extraction}: invalid individual fields are dropped
        rather than rejecting the whole order.
  \item \textbf{Deterministic language heuristics}: avoids an extra model call
        and makes the mirror rule testable offline.
  \item \textbf{Immediate webhook acknowledgement}: avoids Meta retries and
        moves the slow AI and Graph API work to background tasks.
\end{itemize}

\subsection{Risks and Debt}

\begin{enumerate}[leftmargin=1.2em]
  \item \textbf{Main-branch schema drift}. The writer sends
        \code{order\_id}, \code{wilaya}, \code{product\_details} and
        \code{order\_status}; the main schema expects \code{id},
        \code{wilaya\_name} and \code{status} and has no
        \code{product\_details}. A real insert would fail.
  \item \textbf{Incomplete AI branch contract}. \code{ai\_model\_part} adds a
        contract test that imports \code{DERIVED\_COLUMNS}, but the writer on
        that branch does not define it.
  \item \textbf{No durable conversation store}. The \code{AIService}
        dictionary is lost on restart and is not shared between processes. A
        Redis or Supabase-backed store is needed before horizontal scaling.
  \item \textbf{Model state unreliability}. The prompt asks the model for
        \code{conversation\_state}, but the model does not always return it
        reliably. The code compensates with guardrails, monotonic transitions
        and intent markers.
  \item \textbf{Legacy webhook security}. \code{backend/main.py} does not
        verify \code{X-Hub-Signature-256} and does not deduplicate messages.
  \item \textbf{Secrets in source}. The legacy backend has a hard-coded
        fallback verify token, and \code{backend/force\_link.py} has a
        hard-coded access token. They must be rotated and removed.
  \item \textbf{Mock order fallback}. On AI failure, the legacy backend inserts
        a fixed test order. This is acceptable for a demo but would pollute
        production data.
  \item \textbf{Tracked bytecode}. \code{\_\_pycache\_\_/main.cpython-314.pyc}
        is present in some branch trees and should be removed from tracking.
  \item \textbf{No migrations and no CI}. The schema is a raw SQL file, and no
        CI configuration was observed. Schema changes and tests are not
        automatically enforced.
  \item \textbf{PRD and implementation differ}. The PRD mentions 58 wilayas,
        OpenAI or Anthropic, and a Next.js dashboard. The code uses 69
        wilayas, Gemini and no dashboard yet.
  \item \textbf{No merchant dashboard}. The Next.js dashboard is part of the
        PRD and roadmap but is not present in the repository.
  \item \textbf{Base image mismatch}. The documentation says
        \code{python:3.12-slim}; the current Dockerfile uses
        \code{ai-base-env:latest}, which must exist on the build host.
\end{enumerate}

\subsection{Recommended Consolidation Path}

\begin{enumerate}[leftmargin=1.2em]
  \item Choose the canonical database contract and apply it to the schema and
        to \code{order\_store.py} on all active branches.
  \item Define \code{DERIVED\_COLUMNS} and finish the contract test on
        \code{ai\_model\_part}; merge the corrected schema into \code{main}.
  \item Add a persistent conversation store and make the service safe for
        multiple workers.
  \item Harden the legacy webhook or retire it in favor of \code{app.py}.
  \item Remove the hard-coded tokens, rotate them and add secret scanning.
  \item Add migrations, CI and a smoke test that runs against a disposable
        Supabase/PostgreSQL instance.
  \item Add the merchant dashboard or explicitly scope it out of the current
        deliverable.
\end{enumerate}
